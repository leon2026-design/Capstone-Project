# MA-06 Contact Enrichment

MA-06 adds a bounded research and review pipeline alongside the existing MA-05
identity and social-profile workflow. It does not change `Master_Contacts`,
campaign engagement, report parsing, automatic merges, or outreach behavior.

## Current provider support

`djEnrichmentCreateOpenAIProvider()` (`DJEnrichmentOpenAIProvider.js`) is the
live provider (`OPENAI_WEB_SEARCH`). It calls the OpenAI Responses API with the
hosted `web_search` tool (`tool_choice: "required"`) and a strict JSON schema.
See [Live OpenAI web search](#live-openai-web-search-ma-06-live-01).

`djEnrichmentCreateFixtureProvider()` is deterministic synthetic test data
only; it must not be described as live discovery. With no provider, MA-06
creates `NEEDS_RESEARCH` jobs and useful search queries without inventing URLs
or search results. A researcher may add a URL with
`djEnrichmentAddManualCandidate()`.

Live provider capability must be explicitly configured by the caller. A
provider has this shape:

```js
{
  providerId: "AUTHORIZED_SEARCH",
  authorized: true,
  authorizedHosts: ["search.example.org"],
  supportedPlatforms: ["INSTAGRAM", "FACEBOOK"],
  capabilities: {
    searchPublicProfiles: true,
    retrievePublicProfiles: false,
    normalizeUserSuppliedUrls: false
  },
  search: function(query, context) {
    // Use context.fetch(apiName, httpsUrl, options) for outbound requests.
    // Return { candidates: [...] } with source URLs and evidence.
  }
}
```

Only providers marked `authorized: true` are called. Outbound requests must use
`context.fetch()`, which checks HTTPS and the exact `authorizedHosts` allowlist,
disables automatic redirects, and records each request in
`DJ_Enrichment_API_Usage` and the existing `trackedFetch()` API inventory.
Provider search invocations are also counted in each job's `Attempt Count`.
Providers are responsible for honoring any source-specific terms and request
limits. A provider should mark only transient failures with
`error.retryable = true`; invalid credentials and permanent errors are not
retried. Do not fetch restricted profiles or use anti-automation bypasses.

## Workflow

For script-editor use, start with the actual contacts and unresolved observations:

```js
const ss = SpreadsheetApp.getActive();
const result = djEnrichmentRunSelected(
  ss,
  [], // no configured live provider: creates offline research jobs
  { platforms: ["INSTAGRAM", "FACEBOOK", "SOUNDCLOUD", "MIXCLOUD"] }
);
console.log(JSON.stringify(result));
```

For a configured provider, pass it in place of `[]`. To process existing queued
jobs after an interrupted run, call `djEnrichmentResume(ss, providers, options)`.
Processing is bounded by `maxCandidatesPerRun`, `maxProviderRequests`,
`maxApiCallsPerRun`, and `maxAttempts`; `requestDelayMs` can add a bounded delay
between provider calls. No enrichment is scheduled from `Main.js`.

Manual research and review:

1. Use the job's `query` to research through an authorized source.
2. Submit only the real candidate URL/value, evidence, and source URL with
   `djEnrichmentAddManualCandidate(ss, jobId, candidate, researcher, notes)`.
3. Review a supported candidate with
   `djEnrichmentReview(ss, enrichmentId, "APPROVE" | "REJECT" | "NEEDS_RESEARCH", reviewer, notes)`.
4. Transfer an approved social candidate with
   `djEnrichmentTransferApproved(ss, enrichmentId, observationId)`, or
   `djEnrichmentTransferToContact(ss, enrichmentId)` to use the contact's safe
   import observation. The observation must have either a real MA-05
   `APPROVED_LINK` identity review or, if it never entered MA-05 review, exactly
   one `Import_Log` row with outcome `Created` or `Matched` for that single
   contact. Only a `PENDING_REVIEW` profile is saved, via `djSocialProfileSave()`.
5. A reviewer must separately use `djSocialProfileReview()` to verify or reject
   the MA-05 profile. Enrichment approval never verifies it automatically.

An enrichment candidate for an existing contact cannot be transferred unless
the supplied observation is a real observation already linked to that same
contact by an approved review or a safe import decision. This avoids inventing
an observation ID or representing an enrichment source as a promotional report.
An observation with any `DJ_Identity_Review` row still requires an
`APPROVED_LINK`; an import row of `Review identity` or with several contact IDs
is never accepted.

## Storage

The feature creates these sheets only when needed and rejects unexpected
headers:

- `DJ_Enrichment_Jobs` — target, platform, source, query, state, attempts,
  timestamps, and recoverable error details.
- `DJ_Enrichment_Candidates` — separate candidate URLs/values, source,
  confidence ranking, review state, and bounded candidate metadata.
- `DJ_Enrichment_Evidence` — individual evidence values, source URLs,
  timestamps, and deterministic evidence classifications.
- `DJ_Enrichment_Review_History` — manual candidate submissions and
  non-overwritable reviewer decisions.
- `DJ_Enrichment_API_Usage` — each outbound request made through the authorized
  provider context.

Candidate confidence is only a deterministic ranking aid, not an identity
probability. Name-only matches and unsupported profile claims are not verified.
Conflicting candidates cannot be approved. Rejected decisions remain in history.
Spreadsheet-formula-like values are escaped before storage.

Candidate identity is read from the identified `Master_Contacts` row or the
original MA-04/MA-05 observation, not from caller-supplied replacements.
Contacts marked by recognized do-not-contact, do-not-research, or privacy opt-out
columns are excluded. Existing verified profiles, pending candidates, and prior
jobs are reused rather than duplicated. `NOT_FOUND` means only that the
configured source returned no candidate for that query.

## Validation and local demo

Run the focused checks from the repository root:

```powershell
node local-tests\DJEnrichment.test.cjs
node local-tests\DJEnrichmentOpenAI.test.cjs
node local-tests\DJEnrichmentDemo.cjs
```

The demo uses fictional identities, reserved `.test` URLs, and fixture

sets `timeoutSeconds` on each request.

## Live OpenAI web search (MA-06-LIVE-01)

Script Properties (the API key is never logged or written to a sheet):

| Property | Default | Purpose |
| --- | --- | --- |
| `OPENAI_API_KEY` | required | Shared with the extraction provider |
| `OPENAI_RESEARCH_MODEL` | `gpt-6-luna` | Must support `web_search` |
| `OPENAI_RESEARCH_REASONING_EFFORT` | `low` | |
| `OPENAI_RESEARCH_TIMEOUT_SECONDS` | `90` | Clamped to 10–300 |
| `OPENAI_INPUT_USD_PER_1M_TOKENS`, `OPENAI_OUTPUT_USD_PER_1M_TOKENS`, `OPENAI_WEB_SEARCH_USD_PER_1K_CALLS` | unset | Optional; cost estimate only |
| `MA06_PLATFORMS` | `INSTAGRAM,TIKTOK,FACEBOOK,X,YOUTUBE,MIXCLOUD,SOUNDCLOUD,WEBSITE,RADIO_DIRECTORY,BUSINESS_EMAIL` | Explicit properties override this list |
| `MA06_MAX_PAGE_FETCHES` | `4` | Public professional pages inspected per contact (0–6); social networks are not fetched |
| `MA06_MAX_CONTACTS_PER_RUN` | `3` | Maximum 10 |
| `MA06_CONTACT_IDS` | all | Comma-separated test subset |
| `MA06_TIME_BUDGET_SECONDS` | `210` | No new search starts after it |

`runDJEnrichmentLive()` is the explicit entry point, separate from
`runMarketingAgent()`; report processing never waits on or fails because of
research. Each execution:

1. Holds a Script Property lease (`MA06_ENRICHMENT_LEASE`) so overlapping
   triggers skip; an expired lease is taken over.
2. Requeues jobs left `PROCESSING` by an interrupted execution.
3. Queues a small batch of not-yet-researched contacts only when no jobs are
   queued, then processes at most one search per contact. A retryable error
   (429 rate limit, 5xx, timeout, incomplete response, invalid JSON, no search
   executed) leaves the job `QUEUED` for a later run, up to 3 attempts;
   authentication, `insufficient_quota`, and refusals are not retried.
   Existing contacts needing only a few new platform jobs still count against
   the configured contact limit. The time budget reserves room for the OpenAI
   request and bounded page inspections; incompatible settings fail explicitly.
4. Appends a row to `DJ_Enrichment_Run_Log` with requests, web-search calls,
   latency, token usage, estimated cost, and job outcomes.

`reportDJEnrichmentLive()` logs aggregate counts only (no names or URLs).

Only aliases, station/venue, city/region/country, the contact's website, and
existing public profile links are sent. Emails, phone numbers, report contents,
and contact IDs are never sent. A response is accepted only if a `web_search`
call actually ran. Every candidate URL, source URL, and evidence source must be
among that search's returned sources; constructed or remembered profile URLs are
rejected (counted in `usage.rejected`). A social profile that the search did
not list itself can be retained as a review candidate when an excerpt from a
returned page quotes that exact link, e.g. a DJ's Bandcamp bio
"Follow: instagram.com/handle". A search citation is not proof of page content.
The provider downloads a bounded number of returned professional pages and
checks excerpts and explicit social links against their content. It can also
retain requested links the model missed. A cross-link is strong only when the
fetched page contains it and it is attributable to the DJ; unavailable or
unattributed pages do not establish an official cross-link. No provider output
automatically verifies a profile. A shorter handle prefix does not match, and a
quote from a page the search did not return does not count. Name, station, and location claims count
toward MA-06 matching only when quoted in an excerpt from an observed source.
An `OFFICIAL_CROSS_LINK` must come from a page other than the profile itself.
`UNIQUE_ACCOUNT_ID_MATCH` is not accepted from search. Emails must be quoted
from an observed page.

One search per contact serves every platform job for that contact in the same
execution. Only the first job records a `DJ_Enrichment_API_Usage` row, because
only one HTTP request is made. Token and cost totals are in the run log; the
usage sheet's headers are unchanged.

TikTok profiles are accepted only as `tiktok.com/@handle`, reduced from a
video/photo URL if necessary. Instagram profile URLs must be a single
non-reserved path segment, so post, reel, and explore URLs are rejected.
X accepts `x.com` and `twitter.com` account links (including mobile Twitter),
canonicalized to `https://x.com/handle`; a status URL can identify its author.
Search, intent, share and other non-account paths are rejected. YouTube accepts
`/@handle`, `/channel/id`, `/c/name` and `/user/name`, not videos, shorts,
playlists or `youtu.be` links. Facebook vanity and `/people/name/id` or
`/pages/name/id` profiles are supported; post and share links are not accounts.

Facebook, X and YouTube use the existing MA-06 approval and MA-05 verification
workflow. Once verified, their links appear in the existing **Social Accounts**
column of `DJ_Actionable_Contacts` on its next refresh; no new output columns
or changes to campaign history are required. Pending/rejected research links
are not published there. Business email remains review-only.

### Isolated full-report test

The v2 project's test-only `MA06LiveTest.gs` provides
`ma06LiveFullReportConfigure`. Stop its enrichment timer and wait for active
runs to finish before invoking it. This selects **all linked contacts for the
already-imported report**, replacing the 24-contact subset, and configures the
platforms above. It makes no search calls, deletes no checkpoints, resets no
reviews, and does not re-extract the report. If the actionable sheet contains
multiple reports, set `MA06_TEST_REPORT_URL` to the exact **Source Report** value
for the intended report. Missing master-contact associations cause an explicit
error; unresolved identity rows are counted, not silently treated as contacts.

Run `runDJEnrichmentLive` repeatedly or install the isolated enrichment timer.
`remainingQueued: 0` ends a batch, not necessarily the full report: continue
until an execution returns both `queued: 0` and `processed: []`. Prior researched
channels and approved/verified candidates are reused; newly requested channels
are searched. Read `reportDJEnrichmentLive`, `ma06LiveCoverage` and
`ma06LiveCandidates` for counts, exclusions and pending evidence. Manually
validate chosen candidates, approve/transfer/verify them using the existing
workflow, and run `ma06LiveRefreshActionable` to check the final sheet.
The full-report search consumes additional paid API calls; the setup helper
does not start those calls automatically. Remove the enrichment timer at the
end. Do not deploy the isolated helpers or real report data to production or Git.

### Review and auto-approval

Review requirements are unchanged. A candidate becomes `PENDING_REVIEW` only
with strong evidence (an official cross-link) or two supporting signals. A
reviewer still approves it in MA-06, transfers it, and verifies it in MA-05.
Only `VERIFIED` MA-05 profiles appear in `DJ_Actionable_Contacts`.

A possible future auto-approval rule, not enabled here:

- an observed `OFFICIAL_CROSS_LINK` from the contact's known station or
  website domain;
- plus a quoted alias match;
- with no conflicting evidence;
- and no competing candidate on the same platform.

`BUSINESS_EMAIL` candidates are review-only. They do not flow into the
actionable Email column.

### Earlier live feasibility snapshot (isolated test project, Nov 2026)

The figures below describe one specific 17-contact test run and are not a
current benchmark. Subsequent isolated live testing exercised scheduled
enrichment successfully and returned Instagram and TikTok review candidates,
independently checked links from public professional pages, and alternative
professional contact channels. Those later runs are recorded here without
aggregate counts because no reviewed benchmark totals were preserved for this
document. A discovered or source-linked candidate is not an independently
verified identity: it remains subject to the MA-06 approval and separate MA-05
verification workflow described above.

Real OpenAI `web_search` calls (`gpt-6-luna`) over 17 contacts from a real
actionable list: confirmed downloaders, written feedback, station affiliations,
common names, and one existing public link. Aggregate counts only; no DJ data
is committed.

| Measure | Result |
| --- | --- |
| Contacts researched / jobs | 17 / 34 (Instagram + TikTok) |
| Contacts with Instagram candidates | 3 |
| Contacts with TikTok candidates | 0 |
| Candidates with strong evidence (`PENDING_REVIEW`) | 3 |
| Manually validated against sources | 1 verified; 2 plausible but unconfirmed, left pending; 0 incorrect |
| No result | 14 contacts |
| API calls | 34 HTTP 200 (two passes of 17), 41 web-search calls |
| Latency | 6.3 s average, 11.9 s maximum |
| Tokens | 526,921 input, 6,173 output |
| Estimated cost | Not computed; price properties unset |

The first pass found nothing, because the strict grounding rule discarded links
quoted from returned pages. The second pass ran after the quoted-link rule
above and found the 3 candidates. Reasoning effort was `low` for the first pass
and `medium` for the second.

The two unconfirmed candidates are each linked from a real page. One is a
station's link in a third-party station directory rather than the station's own
site. The other is a radio show's Mixcloud bio naming a DJ, but the report gives
only that DJ's name, so nothing ties the page to Brad's contact; a name-only
match is not treated as verified. TikTok links were not found in returned pages
for any sampled contact.
